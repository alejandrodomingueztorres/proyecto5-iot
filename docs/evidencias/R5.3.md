### P3.2 — Dispositivo nuevo sin cambiar Node-RED · Intento 1

| Campo | Valor |
|---|---|
| Requerimiento | R5.3 |
| Ejecutada por | Santiago Osorio (Rol 2) |
| Fecha y hora | 2026-11-11 13:44 (18:44 UTC) |
| Entorno | VM Azure `vm-iot-backend` · `main` en `f679490` · flujo "Proyecto 5 - Ingesta" del Rol 3 desplegado en Node-RED (mismos nodos que `backend/nodered/flows.json`) |
| Precondiciones | `dev03` existe en el broker (usuario y ACL) pero **nunca había publicado**: InfluxDB solo tenía datos de `dev01` y `dev02` |

**Qué se probó:** Que un `device_id` que el sistema nunca ha visto se guarda en InfluxDB sin tocar
Node-RED.

**Cómo (pasos y comandos exactos):** en la VM, desde `~/proyecto5-iot/backend`:

1. Revisar el historial de Node-RED y la suscripción del flujo desplegado:

```bash
git log --format="%h %ad %s" --date=short -- backend/nodered/
docker compose exec -T nodered sh -c 'grep -o "\"topic\": *\"iot/[^\"]*\"" /data/flows.json'
```

2. Lanzar el simulador real (imagen construida desde `device/`) como `dev03`, conectándose por la
IP pública como cualquier dispositivo:

```bash
docker run -d --name p32-dev03 -e DEVICE_ID=dev03 -e MQTT_USER=dev03 -e MQTT_PASSWORD="<clave de dev03>" \
  -e BROKER_HOST=68.211.147.97 -e BROKER_PORT=8883 -e CA_CERT_PATH=/app/ca.crt -e PUBLISH_INTERVAL=5 p5-simulador:p32
```

3. Al minuto, contar en InfluxDB lo que llegó de `dev03` desde el arranque (`T0`):

```bash
docker compose exec -T influxdb influx query --org curso --raw 'from(bucket:"iot") |> range(start: 2026-11-11T18:44:32Z)
  |> filter(fn:(r)=> r.device_id=="dev03") |> group(columns:["_measurement","sensor","_field"]) |> count()'
```

4. Repetir el `git log` del paso 1 y `git status -- backend/nodered/`.

**Resultado esperado:** Los datos aparecen en InfluxDB y Grafana sin ningún cambio en Node-RED.

**Resultado obtenido:**

```
(1) 1b44399 2026-11-08 R5.4: guía de instalación de Node-RED
    a01fa1d 2026-11-08 R5.4: flujo Node-RED (validación, estado y descartes) y evidencia P4.1-P4.6
    43fb333 2026-10-31 chore: estructura de carpetas del proyecto
    "topic": "iot/+/+"
(2) 18:44:34 [dev03] conectado a 68.211.147.97:8883
    18:44:39 [dev03] temperatura=24.7
    18:44:39 [dev03] humedad=53.7
(3) _measurement  sensor       _field  _value
    estado                     online  1
    lecturas      humedad      value   12
    lecturas      temperatura  value   12
    última lectura 18:45:34Z: temperatura 26.1, humedad 49.3 · descartados: 0
(4) mismo git log que en (1); git status sin cambios
```

**Mediciones:** 12 lecturas por sensor en 60 s (una cada 5 s, sin pérdida) y 0 descartados. Al
detener el contenedor, InfluxDB registró `estado online = 0` para `dev03`.

**Captura:** Sin captura de pantalla; evidencia por salida de la terminal.

**Veredicto:** 🟨 Parcial: pasa la parte de InfluxDB; falta Grafana.

**Observaciones:**
- Node-RED no se tocó: ni commits nuevos en `backend/nodered/` ni cambios en el flujo desplegado.
  La suscripción `iot/+/+` adoptó a `dev03` sola.
- La parte de Grafana no se pudo probar: el día de la prueba el Grafana de la VM no tenía data
  source ni dashboard (el dashboard de R5.5 se probó en local). Se repite cuando el Rol 4 lo monte
  en Azure; si el dashboard filtra por `device_id` con una variable, `dev03` debería aparecer sin
  editarlo.
- Al terminar se borraron los puntos de `dev03` en InfluxDB y su estado retenido en el broker,
  para que la demo de R5.8 arranque con `dev03` sin historial.

### P3.3 — Estado retenido · Intento 1

| Campo | Valor |
|---|---|
| Requerimiento | R5.3 |
| Ejecutada por | Santiago Osorio (Rol 2) |
| Fecha y hora | 2026-11-08 13:44 |
| Entorno | VM Azure `vm-iot-backend` · commit `b7f0f67` · Mosquitto 2.0.20 con `persistence true` |
| Precondiciones | dev01 y dev02 de Balena conectados y publicando (el simulador publica `online` retenido al conectarse) |

**Qué se probó:** Que un suscriptor que llega **después** recibe de inmediato el último estado de cada dispositivo.

**Cómo (pasos y comandos exactos):** en la VM, desde `~/proyecto5-iot/backend`, con
`mqtt()` como en [R5.2.md](R5.2.md):

1. Confirmar que dev01 está publicando:

```bash
mqtt mosquitto_sub -h 68.211.147.97 -p 8883 --cafile /certs/ca.crt -u nodered -P "$MQTT_NODERED_PASSWORD" -t 'iot/dev01/+' -v -W 8
```

2. Abrir un suscriptor **nuevo** a `iot/+/status`, mostrando la bandera de retenido (`%r`) y el
tiempo de llegada desde que se lanzó:

```bash
mqtt mosquitto_sub -h 68.211.147.97 -p 8883 --cafile /certs/ca.crt -u nodered -P "$MQTT_NODERED_PASSWORD" -t 'iot/+/status' -v -F '%r %t %p' -W 3
```

**Resultado esperado:** Llega de inmediato el último estado (mensaje retenido).

**Resultado obtenido:**

```
(1) iot/dev01/temperatura {"device_id": "dev01", "sensor": "temperatura", "value": 22.5, "unit": "C", "ts": "2026-11-08T18:44:44Z"}
    iot/dev01/humedad {"device_id": "dev01", "sensor": "humedad", "value": 69.2, "unit": "%", "ts": "2026-11-08T18:44:44Z"}
(2) 0.51 s  retenido=1  iot/dev02/status online
    0.52 s  retenido=1  iot/dev01/status online
```

**Mediciones:** El estado llegó a los 0,5 s de lanzar el suscriptor, lo que incluye arrancar el
contenedor del cliente y el handshake TLS; no hubo que esperar ninguna publicación nueva.

**Captura:** Sin captura de pantalla; evidencia por salida de la terminal.

**Veredicto:** ✅ Pasa

**Observaciones:** La bandera `retenido=1` confirma que el broker entregó el mensaje guardado y
no uno publicado en ese momento. Como Mosquitto tiene `persistence true`, el estado retenido
también sobrevive a un reinicio del broker o de la VM.
